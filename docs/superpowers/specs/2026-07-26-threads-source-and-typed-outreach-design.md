# Дизайн: Threads как источник вакансий + типизированная генерация (вакансия / проект)

- **Дата:** 2026-07-26
- **Статус:** утверждён (brainstorming), готов к плану
- **Область:** `intake-bot/` (детект + чтение поста), `sender/` (резолвер, новый канал, генерация)
- **Связано:** `2026-06-14-intake-platform-detection-design.md`,
  `2026-06-13-multi-platform-outreach-design.md`,
  `2026-07-06-hh-patchright-platform-design.md`

## 1. Проблема

Вакансии всё чаще прилетают ссылкой на **тред в Threads**. Сегодня такая ссылка теряется
целиком. Проверено на живом примере
`https://www.threads.com/@lnkrnchk/post/DbL4LxBl6v9`:

```
detect_contact(url)          -> None            # правила threads нет
is_link_only(url)            -> True
is_fetchable_vacancy_url(url)-> False           # ветки threads нет
```

`ExtractLeadFromText.execute` на `None` кидает `ValueError("no_contact")`, вебхук отвечает
«⚠️ Не нашёл контакт», лид **не сохраняется вообще**.

Вторая, менее очевидная проблема: пост в Threads часто описывает не вакансию в команду, а
**подряд** («нужно сделать сайт / лендинг»). Текущая генерация зашита под вакансию
(`sender/app/infrastructure/openai_client.py:19`: «отклик на вакансию», «читает опытный HR
в крупной компании», «НЕ вставляй ссылки и URL в тело письма»), и для подряда она
неверна по всем осям: читатель не HR а основатель, продавать надо не «возьмите в команду»,
а подход и примеры, а ссылка на портфолио — главный аргумент, который промпт запрещает.

**Цель:** принимать ссылку на тред как полноценный лид, доставать из треда весь текст
вакансии и настоящий контакт, отправлять существующими каналами, а генерацию развести по
типу (вакансия / проект).

## 2. Разведка вживую (2026-07-26, только чтение)

### 2.1. Как Threads отдаёт текст поста

Ключевое и неинтуитивное: **отдача зависит от User-Agent, и зависимость обратная той, что
у hh и LinkedIn.**

| User-Agent | Ответ | `og:description` |
|---|---|---|
| Браузерный (текущая константа `_UA`) | 258 КБ SPA-скелета | **нет** |
| Пустой (заголовок не послан) | 49 КБ | **нет** |
| `facebookexternalhit`, `Twitterbot`, `TelegramBot`, `Slackbot` | 100-104 КБ | **нет** |
| `curl/8.7.1`, `python-httpx/0.27.0`, `Python-urllib/3.12`, `python-requests/2.32.3`, `vacancy-intake-bot/1.0`, `Googlebot` | ~545 КБ SSR | **есть, 480 символов** |

Вывод: работает **непустой не-браузерный UA обычного HTTP-клиента**. Дефолтный
`python-httpx/…`, который intake-bot и так посылает, попадает в эту категорию.
Ни браузерный UA, ни пустой, ни UA соц-краулера не годятся.

### 2.2. Что доступно анонимно, а что нет

| Источник | Что даёт |
|---|---|
| `og:description` | **только корневой пост, обрезанный на 480 символах** |
| `og:title` | `ilij 🤍 alajna (@lnkrnchk) on Threads` → хендл автора |
| Отрендеренная страница (patchright) | корневой пост **+ самоответы автора** + чужие реплаи |
| `Accept: application/activity+json` | отдаёт HTML, content negotiation не работает |
| `graph.facebook.com/.../instagram_oembed` | HTTP 500 |
| `/embed` | только корневой пост |
| `threads.net` | 301 на `threads.com`, контент байт-в-байт тот же |

### 2.3. Почему одного `og:description` категорически недостаточно

Разобранный тред состоит из трёх постов автора:

1. **корневой** (480 символов, попадает в `og:description`) — обрывается на
   «— самостоятельно находить технические решения;»
2. **самоответ автора** — вторая половина требований: «Что важно: опыт с Lovable или
   AI-first инструментами: Claude Code, Cursor, Replit, Supabase…», «Формат работы:
   full-time, удалённо, желательно пересечение с CEST»
3. **самоответ автора** — **контакт:** «Для отклика присылайте портфолио в Telegram:
   @skyluckwalker»

Дальше идут чужие реплаи (в том числе резюме других кандидатов — их брать нельзя).

Самоответов автора в анонимном HTML **нет ни в каком виде** (проверено: `skyluckwalker`,
`Формат работы`, `Cursor`, `Supabase` — 0 вхождений в 545 КБ). Они появляются только при
рендере.

Значит: **на `og:description` этот лид не только теряет половину требований, но и
отклоняется целиком** — контакта нет ни в сообщении, ни в корневом посте.

### 2.4. Прочие факты, влияющие на дизайн

- Автор в отрендеренной странице помечен бейджем **«Автор»** — локализованным. Определять
  самоответы по тексту бейджа нельзя; надо сравнивать username с автором из URL.
- **Неверный username с правильным id поста резолвится в тот же пост.** Идентичность
  поста — это id, username декоративен.
- **Несуществующий id поста** отдаёт страницу **вообще без og-тегов**. Значит фильтр
  generic-заглушки (аналог `_LI_POST_BOILERPLATE_RE`) для Threads не нужен — случай
  отсекается отсутствием тегов.
- **Threads DM не поддерживает документы** — только текст, фото, видео, GIF, стикеры.
  PDF-резюме туда не отправить.
- **DM тому, кто тебя не читает, падает в «Запросы сообщений»** — доставляемость низкая.
- **Threads требует Instagram-аккаунт** вне DMA-юрисдикций (EU/UK/CH). Отключение IG
  автоматически отключает Threads; обратное не автоматически, но в волнах банов 2026
  связанные аккаунты падали вместе. Удалить Threads, не тронув IG, можно.

## 3. Ключевые решения (из брейншторма)

1. **Threads — источник интейка, а не первичный канал отправки.** Приоритет: найти в
   треде настоящий контакт (`@ник` / email / ссылку) и отправить существующим каналом.
2. **Правило Threads идёт последним в `detect_contact`.** Тогда ссылка на тред вместе с
   @ником рекрутера по-прежнему даст telegram — текущее поведение не меняется.
3. **Ленивый резолв (подход A).** Интейк на Vercel сохраняет лид сразу по
   `og:description`; полный тред рендерит ноут в момент отправки. Причина: мгновенный
   ответ бота, лид не теряется при выключенном ноуте, браузер только там, где домашний IP.
4. **Fallback — DM в Threads с отдельного (burner) Instagram-аккаунта.** Личный IG не
   вовлечён. Решение принято с осознанием низкой доставляемости.
5. **CV в Threads не отправляется.** Уходит текст + существующая подпись (в ней уже есть
   Telegram и email). Ссылку на резюме в подпись не добавляем.
6. **Два типа лида: `вакансия` | `проект`.** У каждого свой системный промпт и своя
   секция профиля.
7. **Никакого авто-`skipped`.** Ни классификатор, ни резолвер не имеют права молча
   похоронить лид. При неуверенности — тип по умолчанию `вакансия` и решение за человеком
   на подтверждении.
8. **Дублирование домена между приложениями — принято.** `sender` получает своё
   `app/domain/contact.py`, зеркало интейкового, по тому же паттерну, по которому уже
   раздвоены `sheets_repo.py` и `lead.py`. Общий пакет не заводим.

## 4. Не-цели (YAGNI)

- Публичный реплай в тред как канал отправки.
- Поиск вакансий **по** Threads (аналог `search/*_search.py`). Только приём ссылок.
- Дедуп на пути интейка. Его нет сегодня ни для hh, ни для LinkedIn (дедуп живёт только в
  `candidates_repo` для поиска). Канонизация к id поста оставляет дверь открытой, но сам
  дедуп — вне области.
- Классификация типа для лидов не из Threads. `hh` и LinkedIn `/jobs/` структурно всегда
  вакансия; прогонять их через классификатор — добавить риск сломать работающий путь без
  выигрыша.
- Отдельные типы «стажировка», «не найм». Модель подстраивается под текст в рамках двух
  типов.
- Ссылка на резюме в подписи.

## 5. Интейк (`intake-bot/`)

### 5.1. `app/domain/contact.py`

- `_THREADS_RE` — `threads.com` и `threads.net`, форма `/@user/post/<id>`, со схемой и без.
- `canonical_threads_url(url)` → `https://www.threads.com/@<user>/post/<id>`: срезает
  query (`?xmt=…&slof=1` из шэра) и фрагмент, нормализует `.net` → `.com`.
- `threads_post_id(url)` → id поста, как канонический ключ.
- `threads_author(url)` → `@user` из канонического URL. Это и есть цель для DM до
  резолва; после рендера авторитетным источником становится сама страница (username в
  шэренной ссылке может быть устаревшим — см. §2.4).
- Правило добавляется в `detect_contact` **последним**, после wellfound:
  `Contact("threads", canonical_threads_url(...))`.
- Комментарий-docstring обновляется: порядок приоритетов теперь
  `telegram > email > linkedin > hh > wellfound > threads`.

### 5.2. `app/domain/vacancy_text.py`

- `extract_threads_post(html, max_chars=5000) -> str` — текст из `og:description`, нет
  тегов → `""`. Сущности декодируются, переводы строк сохраняются (они разделяют пункты
  списка) — сигнатура и поведение один-в-один как у `extract_linkedin_post`.
- Автор **через `og:title` не достаётся.** Он выводится из канонического URL
  (`threads_author`), а авторитетно — из отрендеренной страницы в резолвере. Так
  `fetch_vacancy_text` сохраняет свою сигнатуру, от которой зависит `ExtractLeadFromText`,
  и не появляется лишней плюмбинг-трубы для одного хендла.

### 5.3. `app/infrastructure/vacancy_fetcher.py`

- `_THREADS_POST_RE`, `is_threads_post_url()`, включение в `is_fetchable_vacancy_url()`.
- **Per-site User-Agent.** `_get` перестаёт жёстко посылать `_UA`; UA становится
  параметром. Для hh и LinkedIn остаётся браузерный `_UA`, для Threads посылается
  `_CLIENT_UA` (непустой не-браузерный, например `vacancy-intake-bot/1.0`).
  Docstring модуля объясняет, **почему** для Threads браузерный UA ломает всё — иначе это
  будущий тихий регресс при «унификации».
- Ветка в `fetch_vacancy_text` — по образцу существующих: `is_threads_post_url(url)` →
  `extract = extract_threads_post`. Сигнатура не меняется.

### 5.4. `api/webhook.py`

Ответ бота для threads-лида честно сообщает, что текст поста прочитан частично, а полный
текст и контакт дорезолвятся при отправке с ноута.

## 6. Резолвер (`sender/`)

### 6.1. `app/domain/contact.py` (новый)

Зеркало интейкового детекта. Нужен, чтобы прогнать склеенный текст треда и найти в нём
контакт. Threads-правило в этой копии **не нужно** (лид уже threads).

### 6.2. `app/infrastructure/threads_thread.py` (новый)

`resolve_thread(page, url) -> ResolvedThread(text, author_handle)`.

- Открывает канонический URL, ждёт рендера.
- Собирает корневой пост и **самоответы автора**, склеивает в один текст в порядке
  публикации.
- Самоответ определяется **сравнением username с автором из URL**, не по бейджу «Автор»
  (бейдж локализован).
- Чужие реплаи исключаются — в них резюме других кандидатов, которые ни в вакансию, ни в
  письмо попасть не должны.

### 6.3. `app/application/resolve_threads_lead.py` (новый)

1. Рендер треда.
2. `detect_contact(полный текст)`.
3. Нашёл — **одной атомарной записью** на лид (инвариант из коммита `c35619d`) обновить
   платформу, target и текст вакансии; в заметку — «резолв из Threads» + ссылка на тред.
4. Не нашёл — платформа остаётся `threads`, target — хендл автора; текст вакансии
   обновляется на полный.
5. Рендер не удался — ничего не перезаписывается, причина в заметку, статус остаётся `new`.

Вызывается в цикле отправки **до генерации сообщения**: полный текст треда и есть
`vacancy_context`, из которого пишется письмо.

## 8. Типизация и генерация

### 8.1. `app/application/classify_lead_kind.py` (новый)

- Работает **на полном тексте после резолвера**, не на 480-символьном огрызке. Причина: в
  разобранном примере тип подтверждается только вторым самоответом («full-time, удалённо»).
- Модель — **`OPENAI_MODEL`**, не `OPENAI_MODEL_CHEAP`. Разделение в `config.py:15`
  существует потому, что relevance-скоринг идёт по каждой вакансии на каждой платформе в
  каждом запуске; здесь же один вызов на лид, лидов единицы в неделю. Экономить нечего, а
  цена ошибки — целиком неверное письмо.
- Возвращает `{kind, confidence, reason}`. `kind` пишется в **одну новую колонку «Тип»**;
  `reason` дописывается в **существующую** колонку заметки (`COL_NOTE`) — второй правки
  схемы не делаем.
- Включается **только для платформы `threads`**.

### 8.2. `app/infrastructure/openai_client.py`

`_SYSTEM` → `_SYSTEM_VACANCY` (дословно текущий текст, чтобы работающий путь не поехал) +
новый `_SYSTEM_PROJECT`. Отличия проектного промпта: читатель — основатель/заказчик, а не
HR; продаётся подход и примеры, а не «возьмите в команду»; **запрет на ссылки снят**,
потому что портфолио — главный аргумент; уровень и «стек под роль» неуместны.
`generate(...)` получает `kind` и выбирает промпт.

### 8.3. Профиль

`profile.md` остаётся **общим** позиционированием (кто я, чем занимаюсь сейчас, тон,
стиль). Структура сообщения уезжает в `profile_vacancy.md` и `profile_project.md`; код
склеивает общее + нужное по типу. Файла типа нет → откат на `profile.md`, чтобы ничего не
сломалось. `README.md` (раздел «Где править промпт») обновляется.

### 8.4. Переключение типа вручную

В цикле подтверждения рядом с `s/e/r/k/q` добавляется клавиша **`t`**: показывает
текущий тип с обоснованием, по нажатию инвертирует его и перегенерирует сообщение. Это делает ошибки
классификатора бесплатными — для качества результата полезнее, чем ещё один виток
вылизывания промпта.

## 9. Обработка ошибок

Держатся два инварианта: **лид не теряется** (коммит `e2edb49`) и **никогда не
авто-`skipped`**.

| Что сломалось | Поведение |
|---|---|
| Пост удалён/приватный, og-тегов нет | `extract_threads_post` → `("", "")`; уже работающий фолбэк `ExtractLeadFromText` суммаризует сырой текст. Лид сохраняется, бот честно говорит, что текст не прочитался |
| Рендер треда не удался (логин-волл, таймаут, сеть) | Откат на 480 символов из таблицы. Статус `new`, причина в заметку. Короткий текст виден на подтверждении |
| Рендер ок, контакта в треде нет | Fallback `ThreadsChannel` — DM автору |
| Burner-сессия мертва | `ChannelUnavailable` → статус `manual` + ссылка на тред. Это не skip, а «нужны твои руки» |
| Классификатор упал или не уверен | `kind = вакансия` (проверенный путь), в заметке «тип по умолчанию». Никогда не `skipped`, никогда не `failed` |
| Threads ограничил частоту | `RateLimitedError` (уже в протоколе); действуют существующие `MIN/MAX_DELAY_SECONDS` |

## 10. Тестирование (TDD)

**Фикстуры на реальном HTML** (скачан 2026-07-26, кладётся в
`intake-bot/tests/fixtures/threads/`):

- `extract_threads_post` на SSR-странице → 480 символов текста поста.
- Страница без og-тегов (несуществующий id) → `""`.
- Страница-SPA-скелет (тот же URL, но браузерный UA) → `""`, а не мусор.

**Регрессия на User-Agent** (самая важная): запрос к Threads уходит с не-браузерным
непустым UA; браузерный `_UA` для Threads не используется. Без этого теста «унификация»
UA однажды тихо сломает всю фичу.

**`detect_contact`:**
- все формы URL (с query из шэра, `.net`, со схемой и без, с текстом вокруг) →
  `Contact("threads", канонический)`;
- `@lnkrnchk` внутри URL **не** становится телеграм-контактом (сегодня спасает то, что
  `_HANDLE_RE` требует `@` после пробела или начала строки — это надо закрепить);
- URL треда + настоящий @ник в сообщении → побеждает telegram;
- канонизация: `?xmt=…&slof=1` срезается, `.net` → `.com`;
- `threads_author` и `threads_post_id` на всех формах URL.

**Резолвер на поддельной странице** (паттерн уже используется в `test_linkedin_channel.py`
и `test_headhunter_channel.py`):
- самоответы автора склеены в порядке публикации;
- чужие реплаи исключены;
- определение автора работает при **английском** бейдже (`Author`), то есть по username, а
  не по тексту бейджа;
- рендер упал → возвращается пустой результат, лид не портится.

**Классификатор:** корпус реальных постов → ожидаемый тип; разобранный пример → `вакансия`.
Падение API → `вакансия` по умолчанию, не исключение.

**Канал:** `ThreadsChannel` проходит `test_channel_contract.py`; `attachment_path`
игнорируется, а не роняет отправку.

**Логин:** `platforms_needing_login` с новым `LOGIN_ORDER`; `test_wellfound_logs_in_last`
продолжает проходить.

**Живая приёмка фазы 1** (один раз, руками): резолвер на реальном посте находит
`@skyluckwalker` и полный текст требований.
